### Email settings

- Settings reads require current `view_email_settings`; writes require `manage_email_settings`. Both require authenticated selected-account scope. The grants are exposed in Role Manager and are not automatically assigned to custom roles.
- GET returns either persisted settings with an explicit version or documented defaults with version `default`; it no longer persists data. POST uses a strict schema retaining the original integer bounds (1–1,000 per second, 1–1,000,000 per day), conditional account/version updates and monotonically advanced versions. Concurrent default creation conflicts instead of overwriting another writer. Audit logging remains best effort, not a claimed durable audit.
- The settings page is keyed by actor/auth/account, validates server settings/list shapes, cancels old reads, shares a synchronous mutation lock and guards late callbacks/toasts. Missing/failed reads do not expose fabricated editable default settings. Acknowledged saves advance the local version; ambiguous/conflicted writes require reload/reconciliation. Existing account-footer and marketing-default controls are retained; their multi-endpoint saves are not advertised as atomic and stop after an ambiguous/partial result. Their underlying account/list contracts are not converted into versioned transactions by this batch.
- Sender admission in `emailSendLifecycle.ts` is unchanged and its 12 tests pass. The page now describes the actual UTC-calendar-day marketing-attempt budget, not a rolling 24-hour maximum for every kind of email. Reads/default versions can legitimately conflict if the sender initializes settings first.

### Review rematching

- `rematch-reviews.ts` is import-safe. It creates a standalone client only in its guarded CLI entry point. CLI use is **dry-run only**, requires `--account=ID` and `--database=HOST:PORT/DATABASE` matching `DATABASE_URL`, and accepts bounded `--limit=1..200` / ID-keyset `--after` pages. No all-account fallback exists.
- Plans preserve existing/matched links and unavailable/ambiguous cases. A candidate requires a same-account positive Woo customer ID, exact full reviewer/customer/billing email (no plus-address stripping), purchased product and supported order status in the bounded lookback window. Names, absent-email equality, product-only proximity and nearest-date tie-breaking cannot establish identity. More than 500 candidate orders is explicitly unavailable.
- Plans include review fingerprints/versions, proposed order versions, reasons, cursor and digest, without logging plaintext customer emails or database credentials. Exact reviewed pages must be approved independently; no hidden cross-page apply loop exists.
- A separate exported application function requires the exact approved plan/digest and explicit database destination. It re-plans in a serializable transaction, compares the whole digest and uses account/version/unlinked conditional review writes. Changes abort the whole page; no unmatched existing link is cleared. Durable digest-scoped receipts provide repeat acknowledgement and an application record. The CLI deliberately offers no `--apply` shortcut. No real database planning or application was run.

### Learning and AI Manager

Clients cannot spoof AI-derived source, lineage, pending status or approval. New manual rules are explicit user rules; no new automatic derived-rule producer is enabled.
- Updates/deletes/approvals use final account/version predicates; generic updates cannot clear a pending state. Explicit approval consumes only a pending AI-derived version and does not certify effectiveness. Lists have deterministic ordering and fail explicitly above 500 rather than presenting an undisclosed partial rule set. Read routes require current marketing-view authority and validate query booleans.
- Application counters require actor/account/rule/version/stable occurrence and a durable transaction-scoped claim. Merely matching/displaying a rule no longer increments application counts. Unsupported causal-success increments and manual legacy-outcome derivation are unavailable (HTTP conflict), not successful empty derivation. Legacy counters, rules and lineage are not rewritten, deleted or automatically approved; returned success rates are null. Knowledge-base matches no longer promote confidence based on those counters or claim a success percentage.
- AI Manager now separates feature enablement from current `view_marketing` / `manage_marketing` grants. Strict bounded list/filter/refresh/status contracts replace permissive queries. Status writes consume only the selected account's pending recommendation/version; no bare-ID update or reversible timestamp-clearing transition remains.
- Refresh uses a stable user occurrence, durable receipt and account-level transactional admission: at most one new batch per rolling hour, with repeated admitted occurrences returning their receipt. Suggestions use deterministic source/content identities and unique insertion. Changed source records can generate a new review item; identical snapshots do not reappear merely because a timestamp changed. Source failures propagate rather than generating a fake fallback batch.
- Generation is deliberately narrowed to bounded local low-SEO-score product/page/blog review suggestions (4/3/3 records). It no longer invokes the mixed provider/forecast helpers or ranks recommendations by invented savings, uplift or calibrated confidence. Source configuration counts explicitly do not establish usable/healthy connections. API confidence is null, suggestions remain review-only, and the UI labels implemented status as self-reported.

The updated page validates/scopes reads, serializes mutations, handles errors without false empty states and pauses ambiguous writes pending reload. Existing historical AI Manager rows are retained as uncalibrated review items; old prose is not silently rewritten as new evidence.

### Customer merging, sales and tags

- Duplicate candidates require `view_customers`; merging requires current `manage_customers`, different immutable target/source identities, both versions and a stable occurrence. Blank-email/guest records cannot become automatic merge candidates. Candidate reads are deterministic/bounded and disclose truncation.
- The old merge implementation is replaced by a safe service. A serializable transaction/account merge lock reads customers and a bounded order set inside the transaction, applies account/order-version predicates, transfers scoped conversations/reviews and updates enrollments by **account plus Woo customer ID**, never by an unscoped email. Source deletion and a replay receipt commit together. Stale/foreign/over-limit/unsupported merges fail closed.
- Source list memberships or wholesale catalog shares require explicit manual reconciliation before deletion; the service does not drop or invent permissions/memberships. Source guest IDs are rejected. It does not add potentially overlapping/mixed-currency denormalized spend or order totals. Existing target aggregates remain legacy observations, not newly recomputed merged totals.
- Merging is explicitly local. It does not delete the remote Woo customer, prevent later sync recreation, certify search-index freshness or reconcile every external integration. The UI states these limits. Real sync/index reconciliation remains an operator check, not a live operation performed here.
- Merge UI is actor/auth/account/customer scoped and unmounted on close. Reads/acknowledgements are validated, errors stay visible, selection is accessible, confirmation names both immutable records, writes are synchronously serialized and late callbacks/cross-tab events are ignored. Unacknowledged merges block blind retries and direct the operator to reconcile both records. Unverified spend currency is not replaced by a default currency.
- Product sales history is scoped by actor/auth/account/product/page and requires order/customer view access. Reads cancel across scopes and reset pagination. Invalid dates, monetary shapes, duplicate orders or pagination fail into visible retry states. Currency or order totals can be null rather than defaulted to USD/zero; unsafe store URLs are not opened. Pagination/external links are labeled and the table supports narrow/dark views.
- Its supporting API checks the same user grants, bounds the index window to 666 pages of 15, requests exact totals and rejects incomplete inner-hit coverage instead of summing only the first ten lines. Missing currency/money remains unavailable. It describes a local index, not a complete provider ledger. Real Elasticsearch mappings, row formats and refresh lag require staging validation.
- Order tags use actor/auth/account/order scoped mappings, validated tag/color/acknowledgement shapes, synchronous locks, request cancellation and current-attempt guards. The panel tracks the acknowledged advanced order version and pending indexing, does not reuse an old prop version and does not let a late acknowledgement overwrite newer props. Errors are visible and block further writes until reconciliation/reload; native buttons/search and expanded/Escape behavior replace alerts/unlabeled destructive controls. No unknown indexing completion is claimed.

### Traffic classification and privacy

- Classification uses bounded HTTP(S) parsed hostnames and exact/suffix-bound domain lists, with specific Gmail/News/Gemini/Copilot services preceding generic search domains. Query/path provider-name strings and lookalike domains do not impersonate providers. The one path-specific Bing chat rule is bound to Bing's actual hostname. Invalid/non-HTTP referrers are unknown, not direct. Regional domain lists are explicit, not an unsafe wildcard over arbitrary suffixes.
- IP masking validates/parses IPv4/IPv6, expands compressed IPv6 before applying a fixed /48 policy, and masks IPv4-mapped IPv6 using the same /24 representation as plain IPv4. Invalid/zoned/address-like strings become unavailable rather than retaining a partial raw address. Empty input stays empty. Existing stored addresses were not rewritten.
- Short anonymous visits are no longer assumed to be crawlers. Live filtering exposes unknown-user-agent/user-agent-heuristic/fingerprint-heuristic/not-filtered evidence, always with `verifiedBot: false`. Existing Boolean filter compatibility is retained; a user-agent match is not DNS/network verification. Provider/domain coverage and masking are unit-tested, not a claim of complete bot identification or anonymous data under every privacy regime.
