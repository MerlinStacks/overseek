### Recommendation ownership and observations

- Feedback and outcome methods now require account scope, initiating user and fresh `manage_marketing` authority. Final writes use account/resource, lifecycle and `updatedAt` compare-and-set predicates. Missing/foreign/stale/already-consumed writes return a conflict rather than a successful bare-ID update or an invented not-found result.
- Feedback is a versioned pending-to-implemented/dismissed transition. Outcomes can be recorded only once for an implemented recommendation with recorded campaign/ad-account identity, matching account/currency and ordered equal-duration nonoverlapping windows surrounding implementation. Numerical inputs and text are bounded. User-reported observations include reporter, resource, currency, windows and provenance; they are not represented as causal proof or validated historical provider attribution.
- Exact recommendation IDs are preserved, not split at underscores. Logging requires a stable caller-supplied generation occurrence; primary IDs hash account/occurrence/exact recommendation identity for idempotent repeated insertion. Optional resource account IDs are validated against the account. No current tracked caller was silently migrated to an invented occurrence identifier.
- History, time windows and statistics are bounded and validated. Statistics disclose capped status-count coverage; legacy before/after associations no longer produce a causal success rate, “top rules” or confidence-learning score. Failures propagate as errors instead of successful empty/zero output.
- Marketing HTTP producers/consumers were updated for permissions, strict query bounds, mandatory versions and complete observation payloads. The scheduler's old outcome routine is deliberately disabled: it extracted baseline ROAS from arbitrary strings, compared it with account-wide current ROAS and generated supposed successes/learnings. It now reports that comparable observations are required and does not mutate outcomes or derive rules.
- Existing legacy outcomes/learnings were not deleted or rewritten. Manual derivation through `LearningService` still requires its own review and is explicitly in the next ten below; the tracker/scheduler fixes do not certify those historical associations.

### Policy and prompt writes

- Added explicit `view_policies`, `manage_policies` and `manage_ai_prompts` permissions, exposed in Role Manager. Prompt viewing/editing uses the dedicated prompt-management grant. Owner/admin wildcard behavior remains; existing custom roles were not automatically granted new access.
- Policy IDs, document types, text sizes, publication flags and page cursors/limits are runtime-validated. Lists use bounded ID-keyset pages. New documents default to drafts in the editor. New creation uses a client-generated UUID as a stable identity; repeated identical creation with that identity can acknowledge the original row, while conflicting reuse is rejected. This does not promise deduplication across unrelated new create identities or after a user abandons an ambiguous attempt.
- Policy updates/deletes use account/version predicates. Concurrent edits do not silently overwrite or delete another version. Prompt mutations allow only the five known prompt contracts and compare the effective default/override version under an account/prompt advisory lock. The global default row is share-locked during comparison; global defaults are never overwritten by this interface.
- Cache cleanup is non-authoritative and cannot misreport a committed write as failed. Inbox AI's two published-policy consumers now read current, account-bound published policies directly rather than trusting a stale Redis policy copy. Published-policy context is bounded and fails closed rather than silently omitting policies beyond its limit. Monitor the added database reads and review oversized legacy policy sets.
- Removed full policy-body error logging from the route. Normal application error handling retains generic server errors.
- The policies screen is remounted by owner/auth/account, validates paginated documents/prompts and scopes editors by resource/version. Policy/prompt selection is a single discriminated state, so creating a document cannot leave a prompt editor active. Synchronous mutation locks, cancellation and current-attempt guards prevent duplicate submission or old-scope callbacks from installing another editor's result.
- Ambiguous/conflicted writes retain local edits and pause further mutations until explicit discard/reload. Selection changes and page changes ask before discarding local edits; browser unload is guarded. Drafts are not persisted or promised to survive all SPA navigation/logout/account switches. Fields/buttons are labeled, permissions gate mutation controls and the responsive split-pane has light/dark styling. Content remains plain text, not falsely advertised Markdown rendering.

### Inventory and email reporting

- Picklist HTTP requests require selected account/user and `view_orders`, canonical supported statuses and integer limits from 1–500. Invalid input returns HTTP 400 before service execution. Existing fail-closed incomplete-picklist behavior remains unchanged.
- Stock lookups validate scope/identifiers, distinguish parent BOMs from variation BOMs and bound variant/BOM/component reads. Active components must have valid quantities/waste, account-local supported mappings and known managed stock. Duplicate component requirements are combined before calculating independent buildability; nested/self/foreign/missing/ambiguous components return unavailable instead of fabricated zero or skipped demand. Missing variations fail closed.
- Unknown/nonfinite/noninteger stock and malformed attribute shapes no longer produce invented quantities or rendering crashes. Negative known inventory can remain an observed deficit; independent buildability is bounded below by zero. Supplier-only cost rows do not create stock capacity. Unimplemented composite COGS now returns unknown rather than a known zero.
- Variable quantities are summed only when every variant is known and no BOM-derived capacity could share components; truncation or shared/unknown capacity keeps the aggregate null with coverage/provenance. Per-variant capacities remain independent local observations, not a simultaneous fulfillment promise or live-provider verification.
- The stock panel consumes per-variant BOM flags: derived rows are read-only, ordinary variant stock remains editable and a missing aggregate is explained. This batch changes stock reads/display, not the provider-write/recovery protocol of other stock endpoints. No live stock updates were run.
- Email dashboard queries now bind owner/auth/account/window and cancel old reads. Runtime validation, explicit unavailable/error/retry states, period selection accessibility, safe dates and genuine zero-width bars replace stale reads and invented zero KPIs. Existing focus timing/cleanup is preserved.
- Supporting email analytics use a fixed explicit UTC calendar window (including the partial current day), scoped recent unsubscribes, bounded raw trend reads and complete grouped count queries. Over-limit trends are unavailable, not partial zero-filled charts. Send counts are labeled send events; unsubscribes are newly created unsubscribe records.
- Failure share is defined as current `FAILED` message-log rows divided by current terminal-status log rows (`SENT`, `DELIVERED`, `OPENED`, `CLICKED`, `FAILED`, `BOUNCED`, `COMPLAINED`), excluding queued/other statuses. It is not called a provider bounce rate. A missing denominator remains null. These are mutable log-status observations, not a transactional provider-delivery-event cohort.
- Flow/broadcast revenue and currency remain unavailable: legacy event/goal money does not establish persisted currency, deduplicated order identity and verified attribution. Current account currency is not retroactively assigned to those events, and overlapping legacy monetary sources are no longer summed as verified revenue.
