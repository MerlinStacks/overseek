### Critical source events and notification tests

- Added `CriticalEventOutbox`: source transactions persist bounded frozen payloads, stable occurrences, explicit named-subscriber manifests and pending state. Order webhook/sync/bulk local transitions, new review persistence, customer-created webhook materialization, accepted artwork/tracking callbacks and shipping tracking observations now record required work before their state/source acknowledgement. Callback replays require stable bounded source identities; a changed payload under the same identity conflicts instead of creating a replacement occurrence.
- A bounded periodic dispatcher claims only **never-attempted pending** work after every expected handler is installed. Cross-process locks/receipts protect admission. Dispatching/uncertain outcomes retain their source payload and occurrence for reconciliation, not automatic timeout reset/replay. A process restart cannot turn an unknown external outcome into a fresh operation. This is an intentionally conservative handoff, not an exactly-once external delivery guarantee or a full operator recovery UI.
- Automation subscriptions for the recorded event families are named required consumers rather than fire-and-forget listeners. Order/review notification and invoice handlers have the same durable admission. Synchronous/async failures are not disguised as consumer completion. Current tracking opt-in/source chronology is rechecked before queued label-trigger work is admitted; changed/cancelled sources or revoked policy are acknowledged as skipped, not sent. Skip metadata is retained separately from external delivery evidence.
- Legacy `emit()` remains a **best-effort observation** for sockets and operational/UI alerts. It is not a backdoor to the required automation consumers, nor a successful-delivery Boolean. Other operational alert, chat/social notification and socket producers remain explicitly best-effort; this batch does not promise durable delivery for every event in the application. The original unfinished order/artwork/review critical business handoff is no longer dependent on process-local emit.
- Order bulk handling records local transitions and outbox work together after observed provider updates. Provider/local ambiguity no longer triggers the old automatic per-order fallback replay. Preserve the original order/provider outcome for reconciliation; do not call an individual carrier/store mutation merely to discover whether a batch succeeded.
- Notification handlers report partial push/in-app failure and failed outcome logging instead of laundering them as a complete handoff. Invoice email uses a stable order-scoped send identity, requires a configured sender/canonical artifact, escapes dynamic HTML and does not invent dollars/zero for missing money evidence. Raw pre-ingestion IMAP events are not a second conversation notification. Transport acceptance and required-handler acknowledgement are still not proof of customer/device delivery.
- `NotificationEngine.test.ts` now resets mock implementations, restores explicit fixtures, checks missing-currency behavior and partial delivery rejection. Source transaction tests assert outbox handoff occurs inside the source transaction. Separate outbox tests cover frozen ownership, missing handlers, exact replay/conflict, authoritative previous state and uncertain work not being re-dispatched. Existing invoice/notification unit coverage remains; tests do not actually send anything.

### Email account draft, schemas and commands

- `EmailAccountForm` separates scoped draft state from saved-secret presence and rejects account mismatch. Mask markers never become replacement passwords. Record/account/auth changes reset the form and transient action state. Named fields, explicit protocol toggles, TLS, bounded integer ports and HTTPS relay validation replace nested checkbox-in-button controls, parseInt truncation and inferred green readiness. Dirty cancellation is deliberate; mutations/tests share a synchronous lock and preserve unacknowledged drafts/occurrences.
- Saving sends an explicit command envelope and known fields only. The supporting settings owner validates the scoped version/operation acknowledgement before closing; failures are rethrown rather than swallowed as success. Account list reads are bounded/decoded; excessive windows fail unavailable rather than masquerading as a complete truncated list. Delete/default callers carry observed versions and stable command identities. The owner is keyed by account/auth lifetime; an unrelated appearance refresh no longer overwrites a dirty footer draft.
- `routes/email/schemas.ts` centralizes exact integer port parsing, bounded identifiers/text/secrets, strict known keys, enabled-protocol/TLS requirements and credential-free HTTPS endpoints. Unknown keys, fractional/trailing-junk ports and insecure test contracts fail explicitly rather than being silently stripped/truncated. Replacement-secret behavior remains distinct from saved-secret references.
- `EmailAccountCommand` commits local account changes and exact actor/resource/version/payload receipts in the same account-serialized transaction. Saved secrets remain masked in receipts. Mandatory envelopes retire flat/unversioned account writes; external clients must migrate with the web client/API rollout.
- Connection/relay tests require current settings authority plus admin permission, stable source/version/operation admission and charged account work budgets. Saved passwords/relay keys may only be used with their saved destination/identity, never sent to a newly supplied endpoint. SMTP/IMAP sockets have bounded connection/greeting/socket lifetimes and finally cleanup. Relay calls reject redirects, have a deadline and do not reflect arbitrary remote bodies as application messages or delivery proof.
- Network test destinations require **explicit operator opt-in** via comma-separated `EMAIL_CONNECTION_TEST_HOSTS` (exact hostnames) and `EMAIL_RELAY_TEST_ORIGINS` (exact HTTPS origins). Missing configuration disables these network tests; simply opening/editing an account never performs one. This is a deployment-controlled destination policy, not a claim that arbitrary DNS/SMTP servers or every configured production mail transport have been audited. Preserve existing relay admin/saved-endpoint protections and the deployment's egress/DNS/TLS controls.
