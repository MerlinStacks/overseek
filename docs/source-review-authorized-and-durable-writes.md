# Source review: authorized and durable writes

## Implemented

All eight approved actionable files were fixed, including their necessary persistence, worker and client integrations. **`server/src/routes/email/routeHelpers.ts` and `server/src/routes/oauthRouteHelpers.ts` remain untouched**, as approved. ### TikTok connection state

- Replaced self-asserted base64 account JSON with a cryptographically random opaque grant, stored only by hash in the database. The grant records provider, initiating user/account, callback URL, allowlisted relative redirect, expiry and a separately hashed browser proof.
- Authorization requires the explicit `manage_channels` grant (or existing wildcard authority). The browser proof is an HttpOnly SameSite=Lax cookie, Secure in production. Callback state is bounded, browser-bound, provider-bound and claimed exactly once with a conditional database update; unavailable storage fails closed.
- Current connection permission is rechecked before token exchange and before persistence. Provider token identifiers, values and lifetime are validated. Error redirects contain generic fixed codes, not provider/internal error text. Arbitrary absolute, scheme-relative and backslash/control-character redirects are rejected.
- Previously issued legacy TikTok state is intentionally invalid; restart those connection attempts after rollout. This protects the TikTok flow only: the older shared signed-state helper is explicitly identified in the next assessment and is not silently represented as fixed.

### Role decisions and authorization

- Role/assignment schemas bound names, identifiers, permission keys/counts and booleans; cross-account writes use scoped predicates. Role mutation/assignment transactions serialize through an account advisory lock. Assigned roles must be explicitly unassigned before deletion, rather than silently removing user access.
- All affected users have legacy permission-cache entries invalidated after role changes. **Permission decisions now read current database state instead of trusting Redis TTLs**, so failed cleanup cannot keep a revoked cached grant authoritative. Invalid/inherited/truthy permission values are not grants; database failures deny access. Owner/admin/super-admin hierarchy and user-specific override precedence remain explicit and unchanged.
- The tradeoff is additional database reads on the authorization hot path. Monitor production query/pool load; any future caching must preserve revocation correctness rather than silently restoring the old TTL window.
- Added Role Manager choices for `view_inbox`, `manage_channels` and `manage_marketing`. No existing custom role was automatically granted new privileges. Wildcard owner/admin behavior remains unchanged.

### Dashboard writes

- Inbox counts and advertising read/manage endpoints enforce feature-specific permissions. Context, feedback, widget keys/settings and layout coordinates have bounded runtime schemas. Unsupported feedback actions are rejected.
- Main-layout initialization uses a user/account transaction advisory lock and deterministic existing-default selection. Existing duplicate/custom layouts are preserved, not automatically deleted or merged. New cooperating requests no longer race through read-then-create.
- Layout reads are uncached, include a version, and saves require that version. The version is conditionally advanced before widgets are replaced in the same transaction; conflicts do not delete existing widgets. Existing clients that omit the version receive a validation error instead of a destructive last-writer-wins save.
- The dashboard client remounts under owner/auth/account scope, validates reads, serializes queued snapshots using each acknowledged server version and cancels pending debounce work on scope changes. A conflict/ambiguous acknowledgement pauses autosaving and leaves local edits visible. Reload explicitly discards local layout edits. Local widget identities use UUIDs.

### BOM management

- Reads require product/inventory view permission and use bounded keyset pages with page-scoped reason summaries. Child details from legacy foreign-account references are hidden. Reason counts use a safe map; the client follows bounded, advancing cursors and reports incomplete loads.
- Reactivation requires product edit/inventory management permission and validates quantity, waste, exactly one supported component source, tenant ownership, self-reference, nested-BOM limitations and local mapping availability. Woo-linked components require uncached read-only live product/variation existence checks. Unsupported/ambiguous supplier-only mappings require remapping instead of blind reactivation.
- The final conditional transaction checks the validated mapping/ownership fingerprint; concurrent mapping changes fail with conflict. Provider-validation failures leave the item disabled. This action performs no Woo stock write; future sync remains a separate operation. Live component existence can change after a verification read, so downstream sync validation is still required.

### Order tags and search recovery

- Tag mutations require `edit_order_tags` or `edit_orders`, validate bounded tag input/version headers and use Fastify's decoded path once. Literal percent-containing tags no longer receive a second URI decode.
- Account/version CAS updates preserve unrelated current raw data and reject concurrent changes. Updated versions are returned. Tag updates and a coalescing search-index outbox intent commit in the same transaction; failure to record intent rolls back the tag write.
- A scheduler recovery job claims bounded batches with leases, refetches the current account-bound order, uses a bounded indexing request and only deletes the claimed revision. Failed indexing remains durable with bounded backoff; newer intents cannot be erased by an older completion. The API accurately reports indexing as pending rather than implying immediate search consistency.
- Search indexing remains an eventually consistent projection, not part of the order-write transaction. Monitor pending/aged jobs and investigate repeated failures; do not manually delete/reset intents to conceal missing indexing.

### Cohorts, tool dispatch and recommendations

- Retention months require complete integer strings in 1–24. Missing completed retention periods remain null with maturity/method metadata rather than an invented zero or a purported rolling-30-day observation.
- AI tool dispatch accepts only own registered handlers, a nonblank trusted account and strict per-tool argument schemas with bounded integers/enums/text. Caller-supplied tenant overrides are rejected. Logs contain tool/account metadata, not full customer/query arguments. Caller wait is bounded; this deadline does not retroactively cancel underlying legacy handlers that lack cancellation support.
- Keyword scans are bounded and validated, preserve Unicode candidate terms, label absence as absence from the returned sample rather than proof of no visibility, and stop assigning price/currency-independent commercial priority. CTR upside assumptions are explicit heuristics, not forecasts.
- AI generation uses a request deadline, HTTP/body-size checks, complete-response checks and full output validation. Truncated JSON is rejected, not repaired into supposedly complete advice. Unconfigured/failed synthesis is unavailable, not an unexplained successful empty array. API availability/provenance metadata and client notices preserve successful sections while disclosing unavailable ones.

Reads have no deadline/cancellation/late-callback guard, response JSON/message types are unchecked, and editing the address during a pending request can make the result refer ambiguously to a different input. Add attempt-bound serialized submission, bounded email input, generic privacy-preserving success text and accessible loading/error/success status. Do not automatically retry an ambiguous send.
4. **`client/src/pages/ResetPasswordPage.tsx` — high.** Form state and in-flight callbacks are not keyed to the URL token. A response from an old token can clear fields/show success after the link/token changes; duplicate submits can race a single-use reset, letting a later failure overwrite success. Missing/oversized tokens, malformed responses and stalled requests lack adequate guarded states. Scope the form to the reset token, serialize/bound requests, validate acknowledgements, disable consumed-success resubmission, expose accessible statuses and avoid unnecessarily retaining tokens/passwords after completion. Preserve server-side token/password authority; client checks are not that authority.

It lacks a mandatory provider/initiator schema and durable fail-closed single-use guarantee. `buildFrontendUrl` accepts arbitrary absolute destinations; API callback origin can fall back to request host/proxy data. Harden the helper and all affected provider producers/consumers together with durable, provider/initiator-bound claims, strict payload/size/lifetime checks, safe configured origins/relative redirects and no production fallback secret. Arrays/text are trusted at runtime, initial missing scope can leave loading stuck, and stale `data.message` wins over a newer request error. The business-context control ignores the newly explicit `manage_marketing` capability.
