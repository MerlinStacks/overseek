# Guarded receipt transport v1 (staged)

> Historical transport notes. Launch controls, phase-5 operator reconciliation, explicit baselines and atomic verified-proof release now extend this protocol. See [`docs/delivery-launch-api.md`](../../docs/delivery-launch-api.md) for current endpoints, guarantees and remaining verification gaps. The statements below that finalization is absent or permanently inactive no longer describe the implementation.

Implements `server/src/services/deliveryEstimates/receipt-contract.md` on the plugin side. REST registration only loads these classes; private tables are created only during an authenticated, validated receipt request. There are no storefront hooks, public endpoints, activation migrations, release endpoints or automatic account-mode changes.

## Wire protocol

`POST /wp-json/overseek/v1/delivery-estimates/receipts/prepare` and `/apply` reuse existing Woo management permissions and linked-account checks. `X-Overseek-Account-Id` is mandatory; all supplied account aliases must agree. Bodies are limited to 16 KiB and contain exactly:

```json
{"schemaVersion":1,"operation":{"operationId":"receipt_opaque-123","sequence":1,"productWooId":20,"variationWooId":null,"stockOwnerWooId":20,"delta":3}}
```

IDs/sequences are positive safe integers. Operation IDs are account-scoped, case-sensitive `[A-Za-z0-9_-]{1,128}`. Delta is a nonzero integer in `[-1000000,1000000]`. Variations require an explicit parent and independent stock ownership. Simple products require an explicit null variation. Native type, parent, managed-stock state, stock owner, required stock methods and integer quantity are checked at prepare and again before mutation. No ownership setters, absolute stock writes or stock-table SQL are used.

ACKs contain exactly `schemaVersion`, `operationId`, `sequence`, `stockOwnerWooId`, `state`, `stockQuantity`, `guardActive: true`, `receiptSafety: "unverified"`. Prepared/uncertain quantities are null; applied quantities are the original native observed result, including zero. Replaying an applied operation, even after newer operations or deletion of the product, returns its historical ACK without current-stock lookup or journal/guard changes.

## Persistence and concurrency

- `${wpdb->prefix}overseek_receipt_journal` is append-only. Each operation's immutable canonical payload accompanies phase 1 (prepared), 2 (applying), 3 (uncertain), or 4 (applied). Identity and owner/sequence/phase are uniquely indexed per account. No journal updates, deletes or pruning.
- `${wpdb->prefix}overseek_receipt_guards` retains the account/owner's current operation and sequence with `guard_active = 1`. Prepare advances it only by one, after the current operation is final applied. Both tables must actually use InnoDB; otherwise ingestion fails closed.
- Installation reads the engine/existence of each table and issues `CREATE TABLE IF NOT EXISTS` only for a missing table. Replays and normal ingestion of installed tables never issue DDL (even `IF NOT EXISTS` would implicitly commit).
- Caller-owned transactions are rejected before locks/install, before any missing-table DDL, before each owned transaction and before the native stock call. Both `autocommit=0` and an explicit `START TRANSACTION` with `autocommit=1` are unsafe. The check requires native `wpdb` and its existing mysqli handle; it never commits or rolls back caller work. **PHP mysqli does not expose mysqlnd's `server_status` / `SERVER_STATUS_IN_TRANS` bit.** Rather than inventing that property or treating missing status as idle, the implementation uses a unique native `SAVEPOINT`/`RELEASE SAVEPOINT` probe: MySQL ignores the savepoint outside a transaction and release returns exactly 1305/42000; inside a transaction release succeeds and the endpoint rejects it after removing only its own probe. Unexpected results or inability to establish absence fail closed. The existing autocommit check is retained as well. This compatibility choice needs the real MySQL test below, not just stub validation.
- Advisory locks use bounded names and `GET_LOCK(..., 0)`. Lock order is account-scoped operation identity, then physical Woo owner (shared across accounts). Reentrant acquisition is rejected. Partial acquisition is cleaned up in reverse order. Connection ownership is checked before journal commits and native application.
- A busy operation/owner lock returns **409 `overseek_receipt_busy`**, the transport's transient condition. Identity, guard, sequence, missing-prepare and stock-identity conflicts have distinct 409 codes. Invalid envelopes return 400; oversized bodies 413; private storage failures 503. Existing account/permission errors retain their established codes/statuses.
- Prepare commits the immutable operation and active guard atomically without touching stock. Apply commits `applying` before `wc_update_product_stock($product, abs($delta), 'increase'|'decrease')`, with no transaction held across native hooks. Native Woo handles its own stock/cache/hook lifecycle.
- Before prepare/apply, the transport gates on the native `WC_Data_Store` wrapper and exact CPT classes: `WC_Product_Data_Store_CPT` for the stock API's global product store, plus the native product/variation CPT store on the product itself. Custom datastore subclasses/wrappers are rejected with 409 `overseek_receipt_unsupported_stock_store` before applying. Custom `wpdb` drop-ins fail the earlier native-connection check with 503 `overseek_receipt_storage_failed`. Historical applied ACKs still bypass live product/datastore checks.
- **A numeric Woo return is not evidence of a successful write.** Native CPT can ignore a failed `$wpdb->query()` and return a computed quantity. The temporary `OverSeek_Receipt_Write_Observer` requires one native stock-query announcement for the exact owner/direction and exact expected signed-delta CPT SQL, one unchanged issuance through WordPress's `query` filter, and one observed completion with an empty error and exactly one affected row. The observer never executes stock SQL or replaces the native write.
- Observer callbacks exist only inside the guarded native call's `try/finally`. Early `query` filtering captures the previous `last_query`, `last_error`, `rows_affected` and query counter **before WordPress flushes them**. Finalization captures the last query immediately after Woo returns, before journal SQL. This retains a failed stock UPDATE even when later cache/lookup queries clear the error. SQL changes in either Woo or WordPress filters, missing/duplicate writes/announcements, wrong owner/method, zero/multiple affected rows, SQL errors, missing callbacks, recursive query filters and unobservable query-counter gaps all invalidate completion evidence. Observers are removed on every return/exception, without removing other plugins' callbacks.
- The SQL shape is intentionally restricted to the native CPT increment/decrement statement. Future native SQL-shape changes or unreliable observation park the attempt as uncertain rather than treating a computed return or matching current quantity as proof. Dynamic datastore changes during the call are also observed conservatively. This does not claim visibility into arbitrary external inventory writers or direct driver calls that bypass WordPress.
- An exception, invalid native result, failed final capture or process death after the applying barrier cannot permit a second stock call. A surviving applying record becomes uncertain on retry. Neither uncertain replays nor later sequences can mutate that owner. There is no quantity-equality inference or automatic reconciliation.
- Account relinking never borrows another account's guard, sequence, operation identity or ACK. Physical-owner locks still serialize cooperating calls across relinks; linked-account permission is rechecked under locks and before mutation. Relinking is not an inventory cutover/reconciliation mechanism. Existing records remain private and preserved for their original account.

This provides **at-most-one attempted stock application with explicit ambiguity parking**, not exactly-once execution. A crash between the durable barrier and native mutation can park an operation that never changed stock. An uncertain operation may also have changed stock before a hook threw. Other inventory writers do not necessarily take these advisory locks.

Discovery advertises `guardedReceipts: true`, `receiptFinalization: false`. `inboundReceiptSafety` and `storefront` remain false. Guards stay active after success; no verified/finalization state is introduced.

## Verification

Run `php overseek-wc-plugin/tests/delivery-receipts.php` and the existing plugin PHP regression scripts. The standalone harness stubs REST, native Woo and SQL, exercises lifecycle/replay/conflicts/authentication/variations/zero quantities/positive and negative deltas/ambiguity/call counts/relinks/lock cleanup, and asserts the durable applying barrier with no transaction during stock hooks. Its native query trace models WordPress's filter-before-flush ordering: a failed UPDATE returns a fake computed numeric result and subsequent queries clear the error, yet the receipt stays uncertain. Healthy single-row writes (with or without following lookup queries), zero/multiple affected rows, absent/altered/duplicate SQL, hook exceptions, unsupported datastores, dynamic store changes, observer removal and cleanup are covered.

**Limitation:** real MySQL advisory-lock concurrency, connection loss and commit durability, real WordPress query/filter/flush behavior, real native CPT SQL completion, real Woo cache invalidation, and arbitrary third-party native hooks are not integration-tested by this harness. Real database/native-Woo success AND silent-write-failure integration tests and explicit cutover/recovery remain required before enabling guarded transport or storefront estimates. Default legacy mode is unaffected.

### Disposable real Woo/MySQL harness

After installing WordPress and activating WooCommerce and OverSeek in the CI disposable database:

```sh
OVERSEEK_RUN_DISPOSABLE_DB_TESTS=1 wp --path=wordpress eval-file overseek-wc-plugin/tests/delivery-receipts-integration.php --use-include
```

`tests/delivery-receipts-integration.php` refuses mutations unless all three guards hold: `WP_CLI === true`, the explicit environment opt-in is `1`, and `DB_NAME === 'wordpress_tests'`. It additionally verifies the actual selected database name, checks for registered REST routes and rejects an already-active caller transaction before fixture setup.

The harness creates a unique temporary linked account/admin, simple products with stock 10 and an independently managed variation, then uses **real `rest_do_request`** prepare/apply calls. It checks increments, replay, reversal, historical ACKs and persistent active guards. A temporary MySQL `BEFORE UPDATE` trigger signals SQLSTATE `45000` only for the failure fixture's `_stock` row, without altering Woo's SQL text. The test requires uncertain ACK and unchanged DB stock, drops the trigger before replay (so a repeated stock call would succeed and be detected), and asserts no second attempt and blocked later sequence. It also opens a caller transaction with autocommit still enabled and verifies rejection preserves a rollback sentinel.

Prerequisites: stock management enabled; native mysqli/`wpdb` and CPT product datastores; MySQL trigger CREATE/DROP privileges. When binary logging requires it, the **disposable CI service** must already permit trigger creation (`log_bin_trust_function_creators` or appropriate privileged test credentials). The harness does not change global database policy.

Cleanup runs in `finally`: remove only the harness's filter/trigger, delete only its recorded product IDs, purge journal/guard rows only for its unique fixture account, restore the linked option/current user, and delete its temporary administrator. It never drops receipt tables or clears other store data. Test-fixture journal purging is not a runtime reconciliation/deletion API. The parent CI workflow owns invocation of this command.

**Execution status:** passed 62 assertions in an isolated native installation of WordPress 7.1.1, WooCommerce 11.1.1, PHP 8.4.23 and MySQL 8.4.8. The normal success, reversal/replay, active caller-transaction rejection and unchanged-SQL trigger failure paths were exercised; fixtures were cleaned up and the private database process stopped. WP-CLI 2.12.0 requires `--use-include` for this strict-types file; the invocation and CI command include it. The stub harness also passes. This does not establish arbitrary-hook, connection-loss or concurrent-process crash safety, and does not authorize cutover or final guard release.
